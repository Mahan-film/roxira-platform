## GitHub: required checks & agent concurrency

`ci.yml` has 6 jobs: `Detect changes`, `Secret scan (gitleaks)`, `Ruff (non-blocking)`, `Pytest (unit)`, `Compose config`, `Frontend lint + build` (runs `npm run build`, i.e. `tsc` via Next.js, conditional on frontend paths changing). Per `docs/STATE.md`, the `main` ruleset only requires `Detect changes`, `Secret scan`, and `Pytest (unit)`.

- **Gitleaks is already required** (as "Secret scan") — no gap there.
- **`Frontend lint + build` (tsc/next build) is not required.** A broken frontend build can merge today. Recommend adding it as a required check — but because the job is conditional (`if: needs.changes.outputs.frontend == 'true'`), a PR that doesn't touch the frontend produces no check run at all, and a required-but-skipped check blocks merge forever on GitHub rulesets. Fix: either always run the job (fast no-op when nothing changed) or add a tiny always-run wrapper job that reports success/skip, and require *that*.
- **`AGENT_MAX_CONCURRENT` drops instead of queueing.** `agent-task.yml`'s "Enforce concurrency cap" step counts in-progress runs via `gh run list` and, if over the cap, sets `proceed=false` and posts a comment telling the owner to "remove and re-add the `agent` label... once a slot frees up" — i.e. the task is abandoned, not queued; nothing retries it automatically. Proposed fix: replace the manual `gh run list` cap with GitHub Actions' native queueing — give the workflow a shared `concurrency: group: agent-task-pool` (not per-issue) with `cancel-in-progress: false`; Actions then queues excess runs instead of failing them. Since a shared group also serializes issues that should run in parallel up to the cap, the closer fix is: keep the per-issue group as-is, but replace the "abandon" behavior with a re-dispatch — add a `workflow_run` trigger (or a short scheduled sweep) that re-fires deferred issues automatically instead of relying on the owner to notice the comment and re-label.
