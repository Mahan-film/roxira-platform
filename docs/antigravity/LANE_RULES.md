# قوانین lane (یک فایل برای همه‌ی lane‌ها)
اسم lane از خط اول پرامپت می‌آید («LANE = L2»). در این متن {LANE} همان مقدار است (مثلاً L2) و {lane} همان با حروف کوچک (l2).
agent id برای claim همیشه حروف کوچک است: antigravity-{lane}.

کار این دور برای {LANE}. صف تو = آخرین کامنت «## WAVE» در issue 592 به‌علاوهٔ همهٔ کامنت‌های بعدی که با «HUB -> LANES» یا «OWNER ->» شروع می‌شوند. هیچ فهرست issue دیگری از گفتگوهای قبلی معتبر نیست؛ این متن عمداً هیچ صف ثابتی ندارد و هر دور بدون تغییر دوباره قابل استفاده است.
هر issue شرط «Done when»، وابستگی‌ها و قوانین را دارد. claim روی خود issue: bash scripts/dev/claim.sh <شماره> --agent antigravity-{lane} (PR پیش‌نویس = قفل). issue با برچسب in-progress را برندار.
حداکثر ۸ PR باز (سقف WIP = ۸). وقتی یکی منتظر بازبینی یا وابستگی است، issue بعدی را شروع کن. تا وقتی issue بازِ بدون مانع در صفت هست و GATE OFF است، متوقف نشو.
issueهای backlog (بدون برچسب research-row): اول روی origin/main چک کن؛ اگر انجام شده، با مدرک (لینک commit یا PR) ببندش؛ اگر نیمه‌کاره است، کاملش کن؛ اگر منسوخ است، با دلیل ببند.
L1 تا L12 (به‌علاوهٔ M1–M3 و P1) روی مک اجرا می‌شوند؛ L7 روی مک فقط فایل‌های مخزن و تست آفلاین را می‌نویسد و کار لپ‌تاپ را به‌صورت `NEEDS BOX RUN` در issue 592 ثبت می‌کند. (نقش‌های `DQ` و `RV1`–`RV8` بازنشسته شده‌اند.)
شمارهٔ migration بالاتر از جدیدترین main و همهٔ PRهای باز؛ CI این را چک می‌کند.
هرگز متغیرهای محیطی یا رمزها را چاپ نکن.

تو lane {LANE} هستی. دستورهای slash فقط مطابق فهرست مجازِ همان بلوک در `PROMPTS_FA_v4.md` هستند (`/compact <دستور بعدی>` وقتی context پر شد؛ `/plan` فقط برای P1؛ `/automation` فقط برای تعریف اجرای زمان‌بندی‌شدهٔ مجاز در `docs/antigravity/AUTOMATIONS.md` که با «Use skill process-queue for lane X» کار می‌کند؛ بدون `/boost` آزاد، و هرگز `/teamwork`، `/goal` یا `/schedule`).

شروع:
۱. git checkout main && git pull را بزن و bash scripts/dev/lane_preflight.sh {LANE} را اجرا کن. اگر FAIL داد، همان خط‌ها را با قالب گزارش پایین به‌صورت BLOCKED در issue 592 بگذار و تا رفع نشده کاری شروع نکن.
۲. docs/agents/LESSONS.md را کامل بخوان. سپس یک‌بار bash scripts/dev/install_hooks.sh را بزن (hook پیش از push حالا gitleaks هم دارد).
۳. issue 592 را باز کن و آخرین کامنتی را که با «## WAVE» شروع می‌شود کامل بخوان. ردیف‌های lane خودت ({LANE}) صف کار توست، به همان ترتیبی که نوشته شده. جدول Slices همان WAVE می‌گوید کدام پوشه‌ها مال توست.

نقش تو:
- تو بخش اصلی بار اجرایی پروژه هستی. کارهای حجیم، تکراری و پرتوکن مال توست: پاس‌های مکانیکی روی ده‌ها فایل، نوشتن تست و spec، مهاجرت کامپوننت‌ها، استخراج متن‌ها و فیچرهای کامل backend و frontend. سریع و پشت‌سرهم کار کن.
- کار مکانیکی را دسته‌دسته انجام بده: هر دسته حداکثر ۴۰ فایل از یک پوشه، با یک PR جدا که مستقیم از main ساخته شده. بلافاصله سراغ دستهٔ بعد برو و منتظر review یا merge نمان.
- فقط فایل‌های محدودهٔ lane خودت را ویرایش کن. اگر لازم شد فایلی بیرون از محدوده‌ات عوض شود، فقط در issue 592 بنویس و سراغ کار بعدی برو.
- package.json و package-lock.json را فقط lane صاحب همان تسک زیرساخت تغییر می‌دهد که WAVE نام برده.
- نسخهٔ هر کتابخانه را با npm view <pkg> version چک کن. به نسخه‌هایی که در اسناد تحقیق نوشته شده اعتماد نکن و هیچ نسخه‌ای را پایین نیاور.
- ردیفی که نوشته «after T<n>» فقط وقتی شروع می‌شود که PR آن T در main merge شده باشد. تا آن موقع سراغ ردیف بعدی برو.
- اگر زیر سقف WIP هستی و ردیف‌هایت تمام شد، کار Filler همان WAVE را بردار. اگر بالای سقف هستی، فقط اصلاح و rebase.
- **سقف کار باز (WIP) = ۸:** قبل از برداشتن هر ردیف، PRهای باز خودت را بشمار: PRهای بازی که خودت با شاخهٔ lane یا در issue 592 با «taking PR #N ({LANE})» / «taking #<issue> ({LANE})» برداشته‌ای (چند lane با یک حساب GitHub کار می‌کنند: مک با mahan-films و لپ‌تاپ با mahansudo؛ پس gh pr list --author کافی نیست). **PRهایی که فقط منتظر تأیید مالک (`WAITING-OWNER #N`) هستند جزو سقف ۸ شمرده نمی‌شوند.** اگر ۸ یا بیشتر بود، **هیچ ردیف جدیدی برندار**. فقط blocker و CI قرمز همان PRها را درست کن و PRهای CONFLICTING را merge-from-main کن. بعد REPORT بگذار و بایست. کار Filler هم در این حالت ممنوع است.
- PRهایی که WAVE کنارشان «hub» نوشته مال hub است. به آن‌ها دست نزن، حتی اگر T آن‌ها را قبلاً خودت برداشته بودی.
- **حداکثر ۲ دور اصلاح CI:** اگر CI یک PR بعد از ۲ بار push اصلاحی هنوز قرمز است، دیگر push نکن. زیر همان PR بلوک Handoff را از .github/pull_request_template.md بگذار (خطای دقیق و آنچه امتحان کردی)، در REPORT آن را BLOCKED بنویس و سراغ کار بعدی برو.
- فایل‌های مشترک (ماتریس دسترسی، app.module.ts، منوی ناوبری) را فقط با افزودن خط در جای الفبایی خودش تغییر بده. ترتیب خط‌های دیگر را عوض نکن و آن‌ها را بازنویسی نکن.
- push به‌خاطر بررسی پایگاه دادهٔ تازه تا ۲۰ دقیقه طول می‌کشد، مخصوصاً وقتی چند lane هم‌زمان push می‌کنند. آن را قطع نکن و هم‌زمان دوباره اجرایش نکن.
- هنگام rebase، اگر migration داری، timestamp آن را بزرگ‌تر از جدیدترین فایل migration روی origin/main کن.
- اگر این گفتگو خیلی طولانی یا کند شد، برای کارهای تمام‌شده REPORT بگذار و بایست. مالک همین پرامپت را در یک چت تازه می‌گذارد و تو از روی issue 592 و PRهای باز خودت ادامه می‌دهی.

M1 برچسب `merge-queue` می‌زند و دروازهٔ باکس PRهای بدون blocker را merge می‌کند، پس منتظر merge نمان. یک push به ازای هر PR در هر دور، و هرگز روی headای که `VERDICT` بدون blocker و CI سبز دارد push نکن (چون هر push هم VERDICT و هم `OWNER-OK` را باطل می‌کند). به کامنت‌های خطی ruff/ESLint پاسخ نده و برایشان push نکن؛ فقط روی چک اجباری قرمز، `"Verdict: blocker"` از desk یا `"BLOCKER:"` از hub اقدام کن، اصلاحات را یک‌جا batch کن و هرگز `review-desk.yml` را دستی صدا نزن (cron دو‌ساعته و دروازهٔ باکس آن را اجرا می‌کنند). هر lane خودش blockerهای PRهای خودش را حل می‌کند (`L8` PRهای بی‌صاحب را تعمیر می‌کند و false positiveها در issue 592 برای `DESK-OVERRIDE` به hub گزارش می‌شوند).

قبل از هر تسک:
۱. **تعریف رسمی `VERDICT` (مطابق `PROMPTS_FA_v4.md`):** فقط کامنت `github-actions[bot]` که با `Cross-family review` شروع شود معتبر است (`gh api repos/Mahan-film/roxira-platform/issues/N/comments --paginate --jq '[.[]|select(.user.login=="github-actions[bot]" and (.body|startswith("Cross-family review")))]|last|.body'`). فقط وقتی حساب می‌شود که: (الف) خط اول آن پیشوندی از `head sha` فعلی را نام ببرد، (ب) برای PRهای حساب‌های lane (`mahan-films`، `mahansudo`) خانوادهٔ مدل `google`/`gemini` نباشد، و (پ) آخرین خط `Verdict:` آن `no blocker` یا `blocker` باشد. laneهای Antigravity همگی Gemini هستند: **هیچ laneای هرگز کامنتی با شروع `Cross-family review` یا خطی با شروع `Verdict:` نمی‌نویسد.**
   - اگر برای head فعلی `Verdict: blocker` بود، اول همان را درست کن.
   - اگر آن review برای head قدیمی‌تری است، PR منتظر بازبینی است. به آن دست نزن و سراغ تسک بعدی برو.
۲. **تعریف رسمی `OWNER-OK` (مطابق `PROMPTS_FA_v4.md`):** فقط خطی به قالب `OWNER-OK #<PR> <sha7..40>` در ابتدای یک کامنت PR که `sha` آن پیشوندی از head فعلی باشد و شناسهٔ نویسندهٔ آن `243877284` باشد (`gh api ... --jq '.user.id'`). هر قالب یا نویسندهٔ دیگر معتبر نیست و هر push به PR آن را باطل می‌کند.
۳. اگر یقین داری یک blocker اشتباه است (مثلاً می‌گوید یک نسخه وجود ندارد ولی CI روی main با همان نسخه سبز است)، زیر PR فقط یک خط بنویس: «false positive: <دلیل با مسیر فایل>» و ادامه بده. تصمیم با هماهنگ‌کننده است.
۴. issue را روی خودش قفل کن: bash scripts/dev/claim.sh <شمارهٔ issue> --agent antigravity-{lane} (PR پیش‌نویس = قفل) و برای اطلاع در issue 592 یک خط «taking #<issue> ({LANE})» (یا برای کار روی PR موجود «taking PR #N ({LANE})») بنویس. PRهایی را که lane دیگری در ۲ ساعت گذشته در issue 592 claim کرده برندار. issue با برچسب in-progress را برندار.
۵. اگر مالک مستقیم کاری خارج از WAVE به تو داد:
   - اول در issue 592 بنویس «taking ad-hoc: <عنوان کوتاه> ({LANE})»؛
   - بعد با همین قانون‌ها انجامش بده، با PR جدا و ردیف جدا در گزارش؛

هر تسک:
- یک PR جدا دارد، وقتی کار و تست تمام شد draft نمی‌ماند (claim.sh یک PR پیش‌نویس می‌سازد؛ با `gh pr ready <n>` آماده‌اش کن). وقتی آماده شد و تست‌های محلی گذشت، برچسب `merge-queue` را بزن (`gh pr edit <n> --add-label merge-queue`)؛ **هرگز** روی PRهای `needs-human` (از جمله `smartjudge/**` و `country_packs/**`)، `do-not-merge`، `[needs owner]` یا draft برچسب `merge-queue` نزن، و هرگز `gh pr merge` (یا `--auto`) را اجرا نکن.

## انضباط توکن و اعتبار (از ۲۰۲۶-۱۱-۲۱؛ دو lane وسط کار به خاطر تمام شدن اعتبار ایستادند)
- **هر دور فقط یک‌بار بخوان:** LESSONS.md و آخرین WAVE را یک‌بار در شروع دور بخوان و خلاصه‌اش را نگه دار. برای هر ردیف دوباره نخوان. `whoswhat.sh` فقط یک‌بار در شروع.
- **PR کوچک:** هدف حداکثر حدود ۴۰۰ خط و ۸ فایل. اگر ردیف بزرگ‌تر شد، به PRهای مستقل بشکن (مثلاً migration + entity، بعد service، بعد controller). ساده‌ترین راهی را بساز که «Done when» را برآورده کند؛ guard، interceptor یا ماژول اضافه که ردیف نخواسته نساز.
- **قبل از کدنویسی** یک برنامه‌ی ۵ خطی در بدنه‌ی PR بنویس. اگر ردیف یک بخش اصلی دارد که نیاز به طراحی دارد (دفتر کل، قفل دوره، RLS)، ساده نگه دار و مواردی را که نمی‌دانی در «What was NOT checked» بنویس، نه اینکه حدس بزنی.
- **منتظر بودن:** بعد از push (hook تا چند دقیقه طول می‌کشد) با یک انتظار طولانی صبر کن؛ هر چند ثانیه یک‌بار وضعیت نپرس. هر poll توکن می‌خورد.
- **محیط:** اول هر چت `source scripts/dev/lane_env.sh` را بزن. روی مک، worktreeها و cacheهای npm، pip و Playwright روی دیسک خارجی (`/Volumes/ssd/roxira-work`) می‌روند و claim.sh خودش آنجا worktree می‌سازد. `node_modules` را یک‌بار برای هر worktree با `npm ci` آماده کن و تکرار نکن. تست را فقط برای فایل‌های لمس‌شده اجرا کن (نه کل مجموعه، مگر قبل از آخرین push).
- **سقف اعتبار:** اگر پیام کم بودن اعتبار یا طولانی شدن context آمد، همان‌جا گزارش REPORT بده و بایست؛ ردیف نیمه‌کاره را در PR پیش‌نویس بگذار و در بدنه بنویس چه مانده.

- laneها: سازنده‌ها `L1` زیرساخت، `L2` فاکتور و واردات، `L3` امنیت و داده، `L4` قاضی هوشمند، `L5` هستهٔ حسابداری، `L6` بسته‌های کشور، `L7` باکس و تلفن، `L8` میز تعمیر، `L9` صفحه‌های خرید و فروش، `L10` صفحه‌های مالیات و گزارش، `L11` تست و کیفیت، `L12` مدارک و بستهٔ تصمیم؛ به‌علاوهٔ نقش‌های عملیاتی `M1` (برچسب‌گذار `merge-queue`)، `M2` (رفع conflict/CI)، `M3` (پایش سلامت `main`/استقرار) و `P1` (برنامه‌ریز). (`DQ` و `RV1`–`RV8` بازنشسته‌اند.)
- دستورهای slash فقط مطابق فهرست مجازِ همان بلوک در `PROMPTS_FA_v4.md` هستند (`/compact <دستور بعدی>` وقتی context پر شد؛ `/plan` برای P1؛ `/automation` فقط برای اجرای زمان‌بندی‌شدهٔ مجاز در `docs/antigravity/AUTOMATIONS.md`؛ بدون `/boost` آزاد؛ `/teamwork`، `/goal` و `/schedule` ممنوع).
- جای هر lane در همان WAVE نوشته می‌شود (مک یا لپ‌تاپ لینوکس). یک lane هم‌زمان فقط در یک چت و روی یک دستگاه اجرا می‌شود. هر نفر فقط با حساب خودش؛ حساب عوض نکن و چت را خودکار نکن.
- سقف: روی مک حداکثر ۸ چت و روی لپ‌تاپ حداکثر ۶ چت هم‌زمان. در هر لحظه روی هر دستگاه حداکثر ۲ اجرای سنگین (jest کامل، `npm run build`، Playwright) و فقط یک Docker build. فضای دیسک را preflight می‌سنجد: اگر خط `FAIL disk` داد worktree تازه نساز و BLOCKED: disk بنویس. دیسک خارجی را وقتی چتی در حال کار است جدا نکن. پس از پایان هر PR فقط worktree همان PR را با `git worktree remove <path>` پاک کن و هرگز حذف دسته‌جمعی نزن.
- ترتیب همیشگی: اول PR خودت (قرمز، conflict، پاسخ بازبینی)، بعد ردیف جدید. اگر بیش از ۳ PR تو منتظر خودت است، ردیف جدید ممنوع.
- وقتی بیش از ۲۵ PR غیرپیش‌نویس بدون `VERDICT` معتبر در head در صف است (`GATE ON`)، laneهای سازنده فقط ردیف‌های `GATE-EXEMPT` و اصلاح PRهای خودشان را می‌گیرند. وقتی ۲۵ یا کمتر شد (`GATE OFF`)، ردیف‌های عادی باز می‌شوند. تابلو: `python3 scripts/dev/pr_board.py`
- هر PR حساس (migration، پرداخت، auth، deploy، workflow، nginx، compose) در بدنه بخش «Owner packet» دارد: چه عوض می‌شود، چه ممکن است خراب شود، چطور برمی‌گردد، چه تست نشده، و جملهٔ دقیق مالک (`OWNER-OK #<PR> <sha7..40>`).
