# Smart Judge (ghazihoushmand.ir) + Roxira portals: UX / IA / visual audit and redesign plan

Date: 2026-10-11. Code baseline: origin/main @ 6903f22b (#554). Frontend: `output_apps/enterprise_hub/frontend/src`.
Method: live browsing in the in-app browser (375x812 mobile, then desktop), DOM probes via JS (sizes, widths, resource timing), and code reading. Read-only. No login, no OTP, no form submitted, no chat message sent, no upload. Consequences of that:
- I did NOT see a real assistant answer, a streamed draft, the OTP step 2, the live-voice modal, or an actual draft result card. Those are judged from code (`chat-shell.tsx`, `result-view.tsx`, `live-voice-modal.tsx`).
- JS sizes are resource-timing transfer sizes (compressed) on first load; no Lighthouse run.
- The sandbox blocked curl to the sites, so all live checks went through the browser pane.

Owner requirements treated as binding: simpler and lighter; everything inside chat; fields extracted from conversation + uploaded files; ask only for what is missing; forms only as optional "advanced" mode.

---------------------------------------------------------------------
## 0. Executive summary

The product core (chat, voice, upload, honest disclaimers, coverage page) is good and more honest than most. The problems are around it:

1. On a 375 px phone the chat composer has 5 icon buttons + "ارسال", and the text input is **24 px wide** (measured). The primary action of the whole product is nearly unusable on first visit.
2. The first-visit dock (chips + mic hint + composer + privacy note + login nudge + disclaimer + enamad bar) is **346 px of 812 px (43%)**; content gets ~55% and the welcome message is half hidden.
3. Drafting is split into three mechanisms (2 long VIP form pages, 4 canned-prompt chips, header menu pre-fill) with different behaviour, different gating and different look. The VIP gate on the ruling form triggers only **after** the user fills ~5 required fields. Draft chips on an empty chat send a "based on the last conversation" prompt with no conversation.
4. Five visual dialects on one domain (Apple-style `ap-*`, shadcn glass/amber with emoji, indigo/violet Roxira, orange subscription modal, raw zinc `/lawyers`).
5. Brand bleed: `/contact` on the legal site is the Roxira Enterprise sales form; `roxira.ir/about`, `/services`, `/privacy`... serve Smart Judge pages; roxira.net links into Persian RTL pages inside an LTR/`lang=en` shell.
6. Trust copy overclaims ("hallucination approaches zero", "100% matching citations", GDPR, "5,184 nodes" vs coverage page "8 laws / 4,216 articles") and the privacy page says no third parties while prompts go to LLM providers and OTP goes through an SMS vendor.
7. Roxira portal pages have **no mobile menu** (`hidden md:flex` nav, no hamburger).

Single biggest opportunity: replace the forms + chips + menu zoo with one chat surface and a slot-filling "draft assistant" (section 5). Backend endpoints for ruling/indictment already take structured fields; the chat layer only needs an extraction step in front of them.

## 2. Core journeys on mobile (375x812)

### 2.1 First visit -> ask a question
Taps to first answer: type + Send = 2 (good) or tap starter card = 1 (good). Friction before that:
- Dark theme only; first paint shows tip card ("سه نکته برای شروع") + assistant greeting + competence note + guidance + 8 starter cards (4 groups) above the fold of a dock that takes 43% of the screen.
- **Composer input is 24 px wide** (measured `inputW: 24`, viewport 375): clip + camera + mic + phone + "ارسال" (with icon) consume the row. One earlier load of the same page showed 3 buttons and a usable input; the camera/clip buttons arrived with the case-file upload release (#554). Regression of that PR.
- Input is `<input type="text">`: no multi-line, long case descriptions (the whole point) are cramped; Enter sends (on mobile Persian keyboards, Enter should insert a newline or at least not fire during IME composition: no `isComposing` check).
- Mic hint (4 lines) and privacy notice (2 lines) and disclaimer (2 lines) all stack inside the dock; the starter list scrolls under it.
- Disclaimer is permanent and prominent (good), but the same statement appears 4x on one screen (tip card #3, greeting, "ONBOARDING_LINE" on desktop, dock disclaimer).
- Tab/title/H1/footer/menu use five different names for the chat (see 2.8).

### 2.2 Voice
- Mic = record -> stop -> STT -> transcript is **placed into the input**, not sent: 3 taps (start, stop, send) + review. Reasonable for accuracy, but with a 24 px input the review is impossible.
- Phone icon = live call modal (VIP-marketed in /services "✕ for free" but guide says guests get 5/h and logged-in 60/h: contradiction between pricing page and guide).
- Two near-identical glyphs (mic and phone) side by side with no labels; `title` tooltips do nothing on touch. First-time users cannot tell "dictate" from "talk".
- Good: permission/failure/timeout copy is specific; recording status is `role=status`.

### 2.3 Upload
- Clip (file) and camera (direct capture) are separate buttons: right idea for mobile, but the guide says upload is **logged-in only**, and nothing at the button tells a guest that. Expected: tap -> pick -> error/modal (not verified live; I did not upload).
- Limits (15 MB, 30 pages, 5 files, 10/day) live only in the guide. Privacy line under composer ("فایل‌ها فقط برای تحلیل پرونده پردازش...") is good.
- Attachment chips: good states (uploading, error+retry, ready+pages+OCR).
- Missing: "what will you do with this file?" suggestions after upload (summarise, extract parties/dates, draft from it).

### 2.4 Login
- Tap ورود -> modal: phone (placeholder `09xxxxxxxxx`) -> code -> done = 2 screens, ~12 keystrokes. Fine. Guest chat works without login (excellent).
- Modal uses a **violet gradient** button and lock icon: third accent colour vs the blue app theme.
- Helper text "ارقام فارسی و عربی نیز پذیرفته می‌شوند (نمونه: ۰۹۱۲۹۳۶۷۷۹۶)" shows **the real support number** as the sample phone number. Users may type it or call it by mistake.
- Session expiry silently downgrades to guest with a small notice (good, but small 12 px text).

| لایحه دفاعیه | chip -> sends canned prompt | uses "last conversation" | none visible | plain bubble text with a "کپی لایحه" chip; no download/edit |
| دادخواست | chip | same | same | same |
| شکواییه | chip | same | same | same |
| اظهارنامه | chip | same; prompt hard-codes ماده 156 آ.د.م | same | same |

Counts: ruling form = 5 required fields (+ up to 2 duplicates in the court helper) + court choice; 2.9 screens of scrolling; counters on every field (`0/12000`, `0/300`...) are noise. Fields that the model can read from a document (names, court, claims, evidence list) are exactly the ones the form demands.
Other issues:
- `ap-input` has transparent border and black background on a #161617 card: field edges are nearly invisible (measured bg `rgb(0,0,0)`, border alpha 0; ~1.1:1 contrast against the card, fails WCAG 1.4.11 non-text 3:1).
- VIP wall after typing 12,000 characters is the worst conversion/trust moment on the site. Meanwhile `/services` sells a **single draft for 100,000 تومان**, but the form says "ویژه مشترکین VIP".
- Draft pages use a different top bar (`ap-nav`, 3 links) than the rest, so "back to chat" looks different; and they are light/dark by OS while chat is forced dark.
- Terminology: "پیش‌نویس غیررسمی رأی", "پیش‌نویس لایحه قانونی:", "لایحه", "دادخواست" for the same family. Ruling and indictment are judge/prosecutor documents; the majority persona (litigant) needs defense/petition/complaint/notice. They share one flat list.
- Results are not editable in place; "ادله" cannot be added via file.

### 2.6 Upgrade to VIP
Path: chip/menu -> form -> submit -> red/amber error "این امکان ویژه مشترکین VIP است" -> `/services` -> scroll through marketing -> tap buy -> modal (spinner, then 100,000 / 490,000 تومان) -> Zibal. 6+ taps and the price appears on tap 5. Modal on 375 px: tall, clipped at the bottom with page content bleeding through (screenshot), orange gradient CTA, "token packs coming soon" teaser that sells nothing. Phone activation alternative is good for Iran but placed after the CTA.

### 2.7 Finding help
Help = `?` icon (header) -> `/guide` (14 sections, 233 source lines, ~4 phone screens per section). No search, no in-chat "help" prompt, no contact except one phone number. FAQ accordions exist. The `/contact` page is a B2B sales form. Users who get an error ("سرویس موقتاً در دسترس نیست") have only "تلاش مجدد".

### 2.8 Terminology and consistency
- The chat: "گفتگوی حقوقی" (menu), "گفتگوی هوشمند حقوقی" (H1/title), "گفتگوی دادرسی و تحلیل ادله" (footer), "چت دادرسی" (technology CTA), "مشاوره هوشمند" (plans). Pick one: **«گفتگو»** (nav) / page title "قاضی هوشمند".
- Actions: "اقدامات حقوقی" (chip label), "پیش‌نویس‌ها" (menu), "ابزارهای تنظیم متن حقوقی" (guide), "ماژول‌ها و ابزارها" (services). Pick **«دستیار پیش‌نویس»**.
- Plans: "طرح رایگان / Free Tier", "VIP UNLIMITED", "اشتراک نامحدود VIP", "اشتراک ماهانه نامحدود VIP", "سهمیه نامحدود", "لایحه تکی", "توکن" (not real). "نامحدود" is also contradicted by the guide's quotas (voice 60/h).
- Brand: قاضی هوشمند / سامانه هوشمند قاضی هوشمند / Smart Judge; روکسیرا / رکسایرا / Roxira.
- Login: ورود / ورود با پیامک (OTP) / کد تأیید / کد یک‌بارمصرف.
- Digits: code comment says "Latin digits (0-9) everywhere" in `chat-actions.ts`; UI mixes Latin (header, enamad, "0/12000") and Persian (guide, counters via `toLocaleString("fa-IR")`, price). Choose Persian digits for prose and prices, Latin only for phone/ID in `dir=ltr` spans.
- Persian typography: ZWNJ is used correctly in most strings; mixed Latin jargon (Live Voice, OTP, Free Tier, VIP UNLIMITED, GraphRAG) in a consumer UI.

### 2.9 Empty / error / loading states
- Empty chat: strong (starters) but too much stacked; no "recent chats" because history is not built (guide: "به‌زودی"). Closing the page loses the chat; guide tells users to copy their draft. For a legal drafting product that is a serious gap (and weakens the chat-first plan: needs persistence).
- Loading: "در حال تحلیل پرونده..." -> after 8 s timer text (nice). Pinging dot uses `animate-ping` (global reduced-motion rule handles it).
- Errors in chat: bubble + "تلاش مجدد" (good, idempotent).
- Rate-limit copy appears only on hit; guests never see how many messages remain (10/h).
- No offline/slow-network state beyond "اتصال ضعیف".
- Draft form errors: field errors say "مقدار این فیلد معتبر نیست: <server message>" (server text leaked), no focus move to the first invalid field.

## 3. Visual design, accessibility, performance

### 3.1 Hierarchy and layout (chat on 375 px)
- Order from top: header (56) / H1 row / tip card / greeting / competence notes / 4 starter groups / [dock: chips / mic hint / composer / privacy / login link / disclaimer] / enamad bar. Four tiers of "notice" text (`ap-notice` 12 px muted) compete: the user's eye finds no single primary action.
- The one place the user must act (input) is the smallest element on the screen.
- Starter cards: 2-line clamp of a long prompt under a bold title: good scannability, but 8 cards x 3 lines x 4 group titles pushes everything down; show 4 (2 per row) + "more".
- Keyboard: `h-dvh` + `overflow-hidden` + sticky dock should survive the iOS keyboard, but with a 346 px dock a keyboard (~300 px) leaves ~150 px for messages. Collapse notices when the input is focused.

### 3.2 Typography
- Vazirmatn variable self-hosted (`next/font/local`, 45 KB, swap): good. But `--ap-font` (used by every `ap-*` surface) lists `-apple-system, SF Pro...` **before** Vazirmatn: on iOS, Latin/digits render in SF and Arabic-script glyphs may come from system fallback rather than Vazirmatn; inconsistent with the rest of the site that uses Vazirmatn first. Put `var(--font-vazirmatn)` first.
- `DESIGN.md` says the font is loaded via `next/font/google`; the code uses local. Docs stale.
- Sizes: body 17 px (draft pages), bubbles 15 px, `ap-small` 14, `ap-notice/disclaimer/group-title` 12 px, footer 10-11 px. Persian at 12 px with 1.7 leading is hard to read, and the legal disclaimer is 12 px. Minimum should be 13-14 px for any text users must read; 11 px footer/enamad text is below it.
- H1 on draft pages = 40 px on a 375 px screen (breaks "پیش‌نویس غیررسمی / رأی" into two lines) vs 16 px H1 on chat: incoherent scale.
- `line-clamp-2` on Persian starter text clips mid-phrase.

### 3.3 Colour and contrast (WCAG AA)
Computed from tokens (not a tool run, approximate):
- `--ap-text-muted #a1a1a6` on `#000` and `#161617`: ~8.5:1 and ~7:1 pass. Light mode `#6e6e73` on white ~5:1 pass.
- White on `--ap-accent #0071e3` (user bubble, send button): ~4.6:1, borderline pass for 15 px text; fails the 3:1 button-border rule nowhere but is the weakest pair; disabled buttons use opacity 0.5 (white on 50% blue ~2.3:1, acceptable for disabled).
- Input fields: **fail 1.4.11** (see 2.5). Chips: border `rgb(255 255 255 / 0.12)` on #161617 ~1.4:1; the chip's text carries meaning so OK, but the boundary is decorative.
- Amber text (`text-amber-400`) used for footer phone number and warnings on dark: fine; amber on light surfaces (shadcn light mode on static pages) not checked.
- Red/danger `#ff453a` on black ~5.6:1 pass.
- Status colour only: draft status chip uses border colour (warn vs danger) plus text: OK.
- Dark theme consistency: chat/header forced dark; draft pages follow OS; static pages (`/services`, `/about`) use the shadcn `.dark` glass look; login modal and subscription modal have their own gradients; `/lawyers` hard-codes zinc-950. A user switching between chat and a draft page on a light-mode phone gets a white page.

### 3.4 Components and iconography
- Four button systems: `.ap-btn` (Apple blue pill), shadcn `Button`, gradient buttons (violet login, amber/orange pay, indigo Roxira), plain `<button>` with Tailwind classes.
- Emoji used as icons (💎 ⚙️ 🔬 🧠 ⚡ 🗄️ 🎙️ ⚖️ 📚 🛡️ 🔒 🎁 💬) in services, technology, about, privacy, lawyers, contact CTAs: contradicts `DESIGN.md` ("never an emoji ... standing in for an icon") and renders differently per OS.
- Lucide icons elsewhere: consistent stroke; send icon mirrored for RTL (good). Mic vs phone ambiguity (2.2).
- Marketing aesthetic (gradients, glow, "VIP UNLIMITED" in caps) vs the stated design contract ("trustworthy, calm, precise... do not use glossy gradients").

### 3.5 Motion
- Typewriter streaming of fresh answers (`LegalStreamingText`): feels live; verify it never delays copy/scroll; `animate-pulse` on the enamad status dot is a permanent decorative animation (distracting in a legal context) though reduced-motion is respected globally. `animate-ping` loader OK.

### 3.6 Accessibility
Good: `lang=fa dir=rtl`, aria-labels on icon buttons, `aria-live` on voice status, `role=alert` on errors, 44 px touch targets (`--ap-touch`), `:focus-visible` outline, reduced motion, form labels with `htmlFor`.
Gaps:
- Message list has no `role="log"`/`aria-live`: screen-reader users are not told a reply arrived.
- Tooltip-only labels (`title`) for mic/phone/camera.
- No skip link; header nav precedes the chat.
- Dialog semantics for login/subscription modals not verified (focus trap, Esc, return focus): test with a keyboard before shipping changes.
- Counters `aria-live="off"` fine; but "0/12000" on every field is announced as text noise.
- Starter cards are `<button>` with long text: acceptable.

## 4. Trust and conversion

What works: permanent disclaimer under the composer; honest `/coverage` page; "answers from our law base, otherwise general knowledge with a warning"; file privacy note (7-day text retention, no training); enamad 7491439 visible in the footer bar; retry/idempotency; phone support 24 h.

Problems:
1. **Over-claims** that a lawyer or a skeptical user will find: "hallucination approaches zero", "100% matching citations", "GDPR standards", "Dual-Level GraphRAG", "<60 ms retrieval", "5,184 legal nodes including all unity rulings" (about) vs coverage "8 laws / 4,216 articles" vs `/laws` "300 articles" vs services "8 laws". Replace with the coverage numbers everywhere, driven from one source.
2. Model names on public pages ("Claude 5 Sonnet, DeepSeek V4.1, Gemini 3.8 Flash"): AGENTS.md says model ids live in `config/models.yaml`; marketing copy hard-codes them and will go stale/legally awkward. Remove.
3. **Privacy page vs reality**: "never shared with third parties" but prompts go to LLM providers (OpenRouter and model vendors), SMS to Kavenegar (mentioned), payments to Zibal. 5. Pricing is hidden. Show both prices on the plans page and in the lock card. Price 490,000 تومان/month vs single draft 100,000 تومان needs a plain comparison ("3 drafts a month = VIP pays off").
6. No social proof at all, which is appropriate right now (no fabricated testimonials). Better substitutes: coverage numbers, "نمونه خروجی" sample draft (redacted), the 24-hour phone line, the owner/company identity on `/about` (the team line names one manager only; add legal entity, registration/enamad detail, physical address as Roxira's contact does).

8. `/lawyers` pilot: self-declared license number for free VIP, no verification text, no terms: reputational and abuse risk.
9. enamad: link present, but the badge is repeated 2-3 times on full-footer pages (text + badge + id); keep one on chat.
10. Persona mismatch: "قاضی هوشمند" + drafting rulings/indictments reads as a tool for judges, while most visitors are litigants. The first screen should say who it is for: "پرسش حقوقی خود را بنویسید" with two personas in the chips.

## 5. Proposed information architecture

### 5.1 Principles
1. One screen: the chat. Everything else is a sheet, a card, or a short page.
2. Four nav items: **چت | راهنما | اشتراک | حساب**. Info/legal links go to a footer line in the account sheet, not the menu.
3. Drafting is a conversation mode, not a place. Forms survive only as «پیشرفته» inside the draft card ("ویرایش فیلدها").
4. The system extracts, the user confirms: never ask for a field that appears in the conversation, an uploaded file or the profile.
5. Gate at the start (lock card showing price), never after typing.
6. One visual system (the `ap-*` tokens) on every ghazi page; Roxira keeps its own.

### 5.4 Chat-first drafting (design)

Flow:
1. User taps chip «دستیار پیش‌نویس» (or types "لایحه می‌خواهم") -> the assistant shows 4 litigant chips: دادخواست، شکواییه، لایحه دفاعیه، اظهارنامه + "حرفه‌ای" row (رأی، کیفرخواست) for judicial/lawyer users.
2. Entitlement check **now** (plan, remaining drafts). If locked: lock card (price visible, "خرید یک پیش‌نویس ۱۰۰٬۰۰۰ تومان", "اشتراک ماهانه ۴۹۰٬۰۰۰"), and the conversation may continue free up to the intake summary.
3. The assistant extracts a **slot object** from chat history + attachments + profile:
   - ruling: court_type (via `suggestCourt` automatically), claimant, respondent, facts, claims, evidence[] (from uploaded files), jurisdiction.
   - indictment: accused, complainant, facts, charges, evidence[].
   - petition/complaint/defense/notice: parties, subject, amount/date/city, claims, evidence, addressee.
4. It shows a **collected-fields card** (read-only chips: "خواهان: …", "دادگاه: حقوقی (تأیید/تغییر)") and asks **one missing field at a time** as a question bubble with quick replies (e.g. "خوانده کیست؟" [نام را می‌نویسم] [در سند هست، بخوان] [نمی‌دانم]). Minimum viable set only (parties + facts + claims); optional ones become a single "افزودن جزئیات؟" chip.
5. "تهیه پیش‌نویس" button appears in the card as soon as the required slots are filled; also user can say "بسازش".
6. Result = **draft card** in the thread (preview first 12 lines, expand, Edit, Copy, DOCX, PDF, "اصلاح با گفتگو": "بند ۲ را کوتاه‌تر کن" -> new version).
7. Advanced: "ویرایش فیلدها" opens the old form pre-filled with the extracted slots (this is the only place the form exists).

Backend contract (keeps the existing endpoints): add `POST /api/v1/apps/judge/draft/extract` (input: conversation id, draft type, attachment ids -> output: slots + `missing[]` + confidence per slot) and reuse `draftRuling`/indictment endpoints for generation. Server-side DOCX/PDF (Persian RTL: bidi paragraphs, embedded Vazirmatn or B Nazanin, A4, 2.5 cm margins; client-side `docx` package would add ~300+ KB, avoid). Persist drafts + chats (history) so "come back later" works.
