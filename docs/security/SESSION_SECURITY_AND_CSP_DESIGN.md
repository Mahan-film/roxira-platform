## 1. Executive Summary & Problem Statement

In the Roxira enterprise web client (`output_apps/enterprise_hub/frontend`), the browser authentication state is currently managed by `session-store.ts` via `localStorage.getItem("roxira.auth.session")`. This stored payload contains the user's short-lived `accessToken` as well as their long-lived `refreshToken`.

Simultaneously, the platform's production HTTP security headers (`output_apps/nginx_config/snippets/security_headers.conf`) configure a Content-Security-Policy (CSP) that explicitly allows `'unsafe-inline'` scripts:
```nginx
add_header Content-Security-Policy "default-src 'self'; ... script-src 'self' 'unsafe-inline'; ...";
```

### The Security Dilemma
1. **Unprotected Credential Storage (`localStorage`)**: Tokens stored in `localStorage` have no origin-isolation from scripts running within the page. Any JavaScript execution context—whether from a Cross-Site Scripting (XSS) vulnerability, an untrusted third-party script, or an injected dependency—can read `window.localStorage.getItem("roxira.auth.session")` and immediately exfiltrate the `refreshToken`.
2. **Perpetual Session Hijacking**: Because the refresh token is rotated over long periods (7 to 30 days) and grants issuing of fresh access tokens, an exfiltrated refresh token permits an attacker to hijack the session, impersonate the user, access financial ledgers, and bypass MFA until the session family is detected and revoked.
3. **Ineffective XSS Barrier (`'unsafe-inline'`)**: While CSP is designed to neutralize XSS by restricting executable script sources, granting `'unsafe-inline'` completely nullifies script execution defenses, permitting inline `<script>` tags, event handlers (`onload`, `onerror`), and `javascript:` URIs.

This design note specifies the target architecture to permanently eliminate both vulnerabilities:
- **Move the refresh token out of `localStorage` into an `HttpOnly`, `SameSite=Lax`, `Secure` cookie**.
- **Eliminate `'unsafe-inline'` by implementing a per-request cryptographic nonce in Next.js middleware**.
- **Provide a zero-downtime, zero-logout migration path for existing active user sessions**.

## 2. Threat Modeling & Security Invariants

### 2.1 Threat Model
- **T1 (XSS Exfiltration of Persistent Credentials)**: An attacker exploits a DOM-based or stored XSS flaw to read `localStorage`. Under the new design, the refresh token is stored in an `HttpOnly` cookie and is strictly inaccessible to `document.cookie` and `localStorage`, thwarting exfiltration.
- **T2 (Cross-Site Request Forgery - CSRF on Token Rotation)**: Because cookies are automatically attached by browsers to cross-site requests, a malicious third-party site could attempt to trigger `POST /v1/auth/refresh` or `POST /v1/auth/logout`. Mitigated via `SameSite=Lax` cookie semantics, custom request headers (`X-Requested-With` or `Origin` validation), and restricted cookie `Path=/v1/auth`.
- **T3 (Malicious Inline Script Execution)**: An attacker injects inline script payloads into rich-text fields, PDF templates, or URL parameters. Mitigated by removing `'unsafe-inline'` and requiring all executable scripts to carry a cryptographically random, per-request nonce.
- **T4 (Session Invalidation During Rolling Deployments)**: Upgrading the platform must not suddenly terminate existing sessions for hundreds of concurrent accounting, invoicing, and warehouse operators.

### 2.2 Security Invariants
1. **Invariant 1 (`HttpOnly` Invisibility)**: No client-side JavaScript may ever read, write, or inspect the plaintext `refreshToken`.
2. **Invariant 2 (Ephemeral Access Tokens)**: The `accessToken` (JWT) is held strictly in memory (or transient closure state in `auth-client.ts`) and has a maximum lifespan of 15 minutes.
3. **Invariant 3 (Cryptographic Nonce Uniqueness)**: Every HTTP response generated by the Next.js server/edge runtime must generate a unique, cryptographically secure 128-bit (16-byte) base64-encoded nonce. Nonces are never reused across requests.
4. **Invariant 4 (Single Rotation Lock)**: Cross-tab refresh concurrency must continue using the Web Locks API (`navigator.locks.request`) to guarantee that two open tabs never attempt simultaneous rotation of the same refresh token cookie, avoiding false-positive token family revocations.

## 3. Architecture Specification

### 3.1 Cookie-Based Refresh Token Architecture

#### Cookie Attributes
```http
Set-Cookie: __Host-rx_refresh=<opaque_token>; 
            Path=/v1/auth; 
            HttpOnly; 
            Secure; 
            SameSite=Lax; 
            Max-Age=2592000
```
- **Name**: `__Host-rx_refresh` (or `rx_refresh` when deployed across subdomain boundaries such as `app.roxira.ir` and `api.roxira.ir`). The `__Host-` prefix enforces that the cookie is secure, sent only to the host, and has `Path=/`.
- **`HttpOnly`**: Set to `true`. Browser JavaScript (`document.cookie`) cannot read or manipulate it.
- **`Secure`**: Set to `true`. Emitted only over HTTPS connections (in development, relaxed to `false` only if `NODE_ENV !== 'production'`).
- **`SameSite=Lax`**: Provides top-level navigation safety while preventing cross-site POST requests from transmitting the cookie.
- **`Path=/v1/auth`**: Scopes transmission strictly to authentication endpoints (`/v1/auth/refresh`, `/v1/auth/logout`, `/v1/auth/sessions`). Ordinary API calls (`/v1/invoices`, `/v1/ledger`) do not receive the cookie, minimizing overhead and surface area.

#### Endpoint Request/Response Flow
1. **Login (`POST /v1/auth/login`)**:
   - Client sends credentials (`phone`/`password` or OTP).
   - Backend validates credentials, persists token hash in `auth_refresh_tokens`, emits `Set-Cookie: rx_refresh=...; HttpOnly; ...`, and returns:
     ```json
     {
       "accessToken": "eyJhbGciOi...",
       "tokenType": "Bearer",
       "expiresAt": 1732320000,
       "user": { ... }
     }
     ```
2. **Silent Refresh (`POST /v1/auth/refresh`)**:
   - Client detects `accessToken` expiration approaching (via `session-logic.ts: accessNeedsRefresh`).
   - Client acquires Web Lock `roxira-auth-refresh`.
   - Client issues `fetch('/v1/auth/refresh', { method: 'POST', credentials: 'include' })` without request body.
   - Backend extracts cookie `req.cookies['rx_refresh']` (or falls back to body `dto.refreshToken` during migration), verifies token family, issues a rotated refresh token into `Set-Cookie`, and returns new `accessToken`.
   - Client updates in-memory access token.
3. **Logout (`POST /v1/auth/logout`)**:
   - Client issues `fetch('/v1/auth/logout', { method: 'POST', credentials: 'include' })`.
   - Backend revokes session family in database, and clears cookie via `Set-Cookie: rx_refresh=; Max-Age=0; Path=/v1/auth`.
   - Client purges in-memory session.

### 3.2 Nonce-Based Content-Security-Policy (CSP) Architecture

#### Next.js Middleware Implementation (`frontend/src/middleware.ts`)
Next.js 14/15 natively supports per-request nonces in Middleware:

```typescript
import { NextResponse, type NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  // 1. Generate 128-bit cryptographic nonce
  const nonce = Buffer.from(crypto.randomUUID()).toString("base64");

  // 2. Formulate strict CSP
  // 'strict-dynamic' allows scripts loaded by trusted (nonced) scripts to execute
  const cspHeader = `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic' https:;
    style-src 'self' 'unsafe-inline';
    img-src 'self' blob: data: https:;
    font-src 'self';
    object-src 'none';
    base-uri 'self';
    form-action 'self';
    frame-ancestors 'self';
    connect-src 'self' wss: https:;
    upgrade-insecure-requests;
  `.replace(/\s{2,}/g, " ").trim();

  // 3. Forward nonce in internal request headers to React Server Components
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set("x-nonce", nonce);
  requestHeaders.set("Content-Security-Policy", cspHeader);

  const response = NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  });

  // 4. Set CSP on outgoing HTTP response
  response.headers.set("Content-Security-Policy", cspHeader);
  return response;
}
```

#### React Server Component Nonce Consumption
In `frontend/src/app/layout.tsx`:
```tsx
import { headers } from "next/headers";

export default async function RootLayout({ children }: { children: React.ReactNode }) {
  const nonce = (await headers()).get("x-nonce") ?? undefined;
  return (
    <html lang="fa" dir="rtl">
      <head>
        {/* Next.js automatically injects nonce into all internal chunks and scripts */}
      </head>
      <body>{children}</body>
    </html>
  );
}
```

#### Nginx Coordination
In `output_apps/nginx_config/snippets/security_headers.conf`:
- Remove the hardcoded static `Content-Security-Policy` header from Nginx for dynamic HTML pages so Nginx does not conflict with the dynamic nonce header issued by Next.js.
- Nginx retains static fallback headers (HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy).

## 4. Migration & Backward Compatibility Plan

To ensure zero user logout and zero downtime for live users across the transition, the rollout follows a **3-Phase Lifecycle**:

```mermaid
flowchart TD
    subgraph Phase 1: Dual Read & Dual Write
        A1[Client Login / Refresh] --> B1[Backend sets HttpOnly Cookie AND returns refreshToken in JSON]
        C1[Client Refresh Request] --> D1[Backend checks: Cookie present? Use Cookie. Otherwise fallback to JSON body]
    end

    subgraph Phase 2: Frontend Transition
        A2[Client boots] --> B2{Has localStorage refreshToken?}
        B2 -- Yes --> C2[Perform one migration refresh passing body token]
        C2 --> D2[Receive HttpOnly cookie & drop refreshToken from localStorage]
        B2 -- No --> E2[Use credentials: 'include' for all future refreshes]
    end

    subgraph Phase 3: Strict Hardening
        A3[Remove body token acceptance in backend]
        B3[Enforce strict HttpOnly cookie on /v1/auth/*]
        C3[Drop 'unsafe-inline' from production CSP]
    end

    Phase 1 --> Phase 2 --> Phase 3
```

### Phase 1: Backend Dual Mode (`Dual Read & Write`)
1. In `AuthController.login` and `AuthController.refresh`:
   - Emit `Set-Cookie: rx_refresh=<token>; HttpOnly; Secure; SameSite=Lax; Path=/v1/auth`.
   - Maintain `refreshToken` field in JSON response for legacy clients.
2. In `AuthController.refresh` and `AuthController.logout`:
   - Inspect `req.cookies['rx_refresh']`. If present, validate and rotate via cookie.
   - If cookie is absent, fallback to `dto.refreshToken` in request body.

### Phase 2: Frontend Transparent Migration
1. `session-store.ts`:
   - On session load, if `session.refreshToken` is present in `localStorage`:
     - Issue migration refresh: transmits `dto.refreshToken` to backend once.
     - Upon receiving `Set-Cookie`, strip `refreshToken` from `localStorage` (`delete session.refreshToken; writeSession(session)`).
   - All subsequent refreshes invoke `fetch(AUTH_ENDPOINT, { method: 'POST', credentials: 'include' })` with empty body.

### Phase 3: CSP Nonce Activation & Final Cutover
1. Enable Next.js Nonce Middleware in `frontend/src/middleware.ts`.
2. Remove static `'unsafe-inline'` script directive from Nginx configuration.
3. Turn `dto.refreshToken` in backend to optional/deprecated, validating exclusively via cookie.

## 6. Verification & Acceptance Criteria

1. **Cookie Verification**: Inspecting `POST /v1/auth/login` and `/refresh` responses demonstrates `Set-Cookie` header with `HttpOnly`, `Secure`, `SameSite=Lax`, and `Path=/v1/auth`.
2. **Storage Audit**: `window.localStorage.getItem("roxira.auth.session")` contains strictly `accessToken`, `user`, and `expiresAt`; no refresh token string is visible.
3. **CSP Audit**:
   - `curl -I https://app.roxira.ir/login` returns `Content-Security-Policy` with `nonce-...` and without `'unsafe-inline'` under `script-src`.
   - Chrome / Firefox DevTools console shows zero CSP violation errors for native application scripts.
4. **Cross-Tab Concurrency**: Opening 5 concurrent browser tabs simultaneously after access token expiry results in exactly 1 token rotation via WebLock, updating all tabs cleanly without session eviction.
5. **Reversibility & Rollback**: Reverting the cookie flag preserves compatibility with legacy body-based refresh tokens.
