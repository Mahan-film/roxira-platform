# برنامه ورود داده با کمک هوش مصنوعی (AI-assisted data import)

مالک درخواست: ۱۴۰۵/۰۷/۲۲ (2026-10-14) — مشتری فایل خروجی نرم‌افزار قبلی
(CRM/حسابداری/ERP) را بارگذاری می‌کند و داده به‌صورت خودکار نگاشت و وارد می‌شود.

> وضعیت: **MVP سرنخ‌های CRM** پیاده‌سازی شد (`modules/data_import` +
> `frontend/src/app/crm/import`). گسترش به ماژول‌های دیگر در ادامهٔ همین سند
> طراحی شده و **تنها پس از تکمیل موج جداسازی مستأجر همان ماژول** مجاز است.

## ۱. قواعد سخت (غیرقابل نقض)

1. **داده مشتری هرگز به مدل رایگان/`may_log` نمی‌رود.** تنها تماس مجاز LLM:
   OpenRouter با کلید سروری `OPENROUTER_API_KEY`.
2. **مدل** فقط از نقش `cheap` در `config/models.yaml` خوانده می‌شود
   (`modules/data_import/services/openrouter-mapping.service.ts`
   → `readCheapModelId`). هیچ شناسه‌ای hardcode نمی‌شود. مسیر فایل به‌طور
   خودکار از چند نامزد (شامل ریشه مخزن) امتحان و در صورت نیاز با متغیر محیطی
   `MODELS_CONFIG_PATH` بازنویسی می‌شود؛ اگر فایل خوانده نشود، فراخوانی LLM
   انجام **نمی‌شود** و نگاشت قطعی جایگزین می‌گردد.
3. **بدنه درخواست** همواره `provider: { data_collection: "deny" }` دارد.
4. **حداقل داده به مدل:** فقط سربرگ ستون‌ها + حداکثر **۵ ردیف نمونه**، و هر
   سلول به **۴۰ نویسه** بریده می‌شود (`MAX_SAMPLE_ROWS` / `MAX_CELL_CHARS` و
   تابع خالص `buildMappingRequestBody`). ردیف کامل هرگز به مدل نمی‌رود.
5. **شناسه مستأجر** تنها از `requireTenantId(request)` (پیلود JWT) — هرگز از
   بدنه/کوئری/هدر. بارگذاری در حافظه با کلید `tenantId + uploadId` و TTL
   ۳۰ دقیقه نگه داشته می‌شود (هرگز روی دیسک داخل مخزن).
6. **نوشتن** فقط از طریق `CrmRepository` موجود (`createLeads`/`createLead`)،
   پس هر ردیف `tenant_id` فراخوان را می‌گیرد.
7. **دسترسی** فقط `request.user.role === 'ADMIN'` یا `tenantRole === 'OWNER'`.
8. **Fallback قطعی:** اگر LLM ناموفق باشد یا نگاشت خالی برگرداند، نگاشت
   مترادف فارسی/انگلیسی (`buildFallbackMapping`) جایگزین می‌شود.

## ۲. جریان MVP (سرنخ‌های CRM)

```
POST /v1/enterprise-hub/data-import/crm-leads/preview   (multipart, ≤5MB, ≤5000 rows)
  → parse CSV → 5 ردیف نمونه → OpenRouter(cheap, deny)
  → { uploadId, headers, sampleRows, mapping, mappingSource, totalRows }

POST /v1/enterprise-hub/data-import/crm-leads/commit    { uploadId, mapping }
  → اعتبارسنجی هر ردیف با CreateLeadDto
  → رد تکراری بر پایه (tenantId, email) — شامل تکرار داخل خود فایل
  → درج گروهی (بسته‌های ۲۰۰تایی، با پشتیبان درج تکی)
  → { imported, skipped, errors:[{row, reason}] }  (حداکثر ۵۰ خطا)
```

- **نسخه فعلی CSV-only است.** در `package.json` این پکیج هیچ کتابخانه‌ای مثل
  `xlsx` یا `papaparse` وجود ندارد؛ بنابراین فایل `.xlsx` با پیام روشن رد
  می‌شود («پردازش فایل اکسل در این نسخه پشتیبانی نمی‌شود؛ لطفاً CSV»).
  افزودن پشتیبانی XLSX یک کار جداگانه و نیازمند افزودن وابستگی است.
- پارسر CSV داخلی (`parsers/csv.parser.ts`) از نقل‌قول دوگانه، جداکننده‌های
  `, ; tab |`، خط‌پایان CRLF و BOM پشتیبانی می‌کند.
- نگاشت پیشنهادی در UI با منوهای ویرایش‌پذیر قابل اصلاح است.

## ۳. گسترش به ماژول‌های دیگر (هر کدام فقط پس از موج جداسازی مستأجر آن ماژول)

طرح کلی برای همه یکسان است: `preview` (تجزیه + نگاشت LLM) و `commit`
(اعتبارسنجی DTO + رد تکراری + درج از طریق Repository همان ماژول با
`tenantId` فراخوان). تفاوت‌ها:

### ۳.۱ اقلام انبار (Inventory items)
- **پیش‌نیاز:** تکمیل موج جداسازی مستأجر ماژول `inventory` و اطمینان از
  tenant-scoped بودن `InventoryRepository`.
- فیلدهای هدف: `sku`, `name`, `unit`, `category`, `reorderPoint`, ...
- کلید یکتایی پیشنهادی برای رد تکراری: `(tenantId, sku)`.
- پیچیدگی: نگاشت واحدهای اندازه‌گیری و دسته‌بندی‌ها به واژگان داخلی.

### ۳.۲ دفتر حساب‌ها و اسناد روزنامه (Chart of accounts / journal)
- **پیش‌نیاز:** موج جداسازی مستأجر `accounting` + تضمین بستن دوره‌ها.
- فیلدهای هدف: `accountCode`, `accountName`, `accountType`, و برای اسناد
  `date`, `debit`, `credit`, `description`. **توجه:** Balanced-entry باید
  پیش از درج اعتبارسنجی شود؛ import نباید سند نامتوازن بسازد.
- کلید یکتایی: `(tenantId, accountCode)`.
- این ماژول حساسترین است: ورود باید تراکنشی و قابل بازگشت (reversal) باشد.

### ۳.۳ فاکتورها (Invoices)
- **پیش‌نیاز:** موج جداسازی مستأجر `invoicing` + قواعد انطباق مالیاتی/مودیان.
- فیلدهای هدف: سرصفحهٔ فاکتور + اقلام. کلید یکتایی: `(tenantId, invoiceNumber)`.
- نگاشت شماره‌های مالیاتی/شناسه کالا **نیازمند بررسی** است (خطر عدم انطباق).

### ۳.۴ منابع انسانی (HR)
- **پیش‌نیاز:** موج جداسازی مستأجر `hr`.
- فیلدهای هدف: کارمند (`fullName`, `nationalId`, `position`, `contractStart`)
  و احکام/فیش حقوقی. این داده شخصی بسیار حساس است: نگاشت باید فقط با
  `provider.data_collection: "deny"` و بدون ارسال شناسه‌های ملی به مدل باشد
  (سلول‌های حساس بهتر است پیش از ارسال mask شوند).

> **شرط مشترک:** هیچ ماژولی تا زمانی که جداسازی مستأجر آن (tenant isolation
> wave) تکمیل و تست‌نشده باشد، مجاز به ورود داده نیست. ورود داده یک مسیر
> نوشتن انبوه است و کوچک‌ترین نقص جداسازی به نشت بین‌مستأجری تبدیل می‌شود.

## ۴. قالب‌های خروجی شناخته‌شده نرم‌افزارهای ایرانی — «نیازمند بررسی»

فهرست زیر فرضی/مقدماتی است و باید با نمونه فایل واقعی مشتری بررسی شود:

| نرم‌افزار | قالب احتمالی | وضعیت |
|---|---|---|
| سپیدار (Sepidar) | CSV/Excel خروجی «مشتریان/طرف حساب‌ها» و «کالاها» | **نیازمند بررسی** |
| همکاران سیستم (Hamkaran) | Excel/XML خروجی ماژول فروش و حسابداری | **نیازمند بررسی** |
| هلو (Holoo) | DBF/CSV قدیمی، کدگذاری ویندوزی (۱۲۵۶) | **نیازمند بررسی** |
| محک (Mahak) | CSV/Excel لیست مشتریان و فاکتورها | **نیازمند بررسی** |

نکات مهم این فایل‌ها:
- **کدگذاری:** بسیاری با Windows-1256 یا Windows-1252 ذخیره می‌شوند؛ پارسر
  فعلی UTF-8 فرض می‌کند. افزودن تشخیص کدگذاری **نیازمند بررسی** است.
- **جداکننده:** جداسازی با `;` در خروجی‌های فارسی رایج است (پارسر فعلی تشخیص
  خودکار دارد).
- **سربرگ‌های فارسی:** بخشی با نگاشت مترادف فعلی پوشش داده می‌شود، اما
  برچسب‌های تخصصی هر نرم‌افزار **نیازمند بررسی** و افزودن به مترادف‌هاست.
