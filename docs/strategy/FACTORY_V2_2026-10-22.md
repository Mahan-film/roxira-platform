# Software factory v2 — parallel AI teams that ship verified work (2026-10-22)

Goal (owner): build any module, product or technology faster, cheaper and in parallel, with teams of
agents on many model APIs, so all strategies move at once — without the hub's (Claude's) limits being
the bottleneck and without broken releases.

## 2. Lessons from today (evidence)
1. Unit tests + typecheck are not enough: the database import passed 395 tests and still wrote 3 of 31 accounts,
   0 journal lines and no undo batch. Only an end-to-end run on real data found it.
2. "Merged" ≠ "deployed": every claim of done must be checked against `autodeploy-last.json`.
3. Cheap models finish ~60–70 % of large tasks; the rest time out or leave one tsc error. A hub fix of 1–2
   lines then finishes them — cheap overall if the task is split well.
4. Agents cannot install dependencies; the hub must add deps first (done for sql.js, fflate, S3, MCP SDK).

## 3. v2 design: teams, lanes and gates
```
owner idea / strategy doc
   └─ Architect (hub, strongest model; 1 call): contract-first spec — API contract, DB migration, file list,
      acceptance test (E2E script + fixture) — split into ≤ 300-line tasks per lane
        ├─ Lane BE   (cheap coder: DeepSeek / GLM / free ladder)  ┐
        ├─ Lane FE   (cheap coder)                               ├─ run in parallel, each in its own worktree
        ├─ Lane DATA (cheap coder: migrations, fixtures)          │   or Daytona sandbox
        └─ Lane TEST (cheap coder writes the E2E + fixtures FIRST)┘
   └─ Gate 1 workbench: tsc / lint / unit tests (exists)
   └─ Gate 2 build: docker build of every changed image (new — would have caught the mcp/ deploy failure)
   └─ Gate 3 E2E: isolated sandbox with prod schema + fixture, acceptance script must pass (new)
   └─ Reviewer: a different model family reads the diff + gate outputs (exists as a skill; automate)
   └─ Merge → autodeploy → Gate 4 post-deploy check: deployed SHA == merged SHA and smoke ok, else alert (new)
```
Rules: every task names its acceptance check; a task that changes a Dockerfile-copied tree must pass Gate 2;
a task that touches import/accounting/payments must pass Gate 3.

## 4. Capacity and cost (use every key, stay under limits)
- **Model pool**: LiteLLM key pool already rotates Groq / Gemini x4 / Mistral / OpenRouter free → paid
  DeepSeek / GLM. Add per-provider daily budgets and route by lane (coding: DeepSeek/GLM; review: a different
  family; long context: Gemini). Claude stays architect/reviewer only.
- **Compute**: srv1 for orchestration only; checks and E2E in **Daytona** (5 GB free disk, owner has 4+ keys);
  GPU jobs on **Modal** (account 1 + fallback account 2, $30/month each); embeddings on Cloudflare Workers AI.
- **Queue**: raise parallelism from 5 to 8 when checks move to Daytona; daily attempt cap per lane, not global,
  with a Telegram alert when hit (today it stalled silently).

## 5. Candidates to evaluate (not adopted yet)
OpenHands / SWE-agent style autonomous agents for whole-feature runs; Aider for focused edits; E2B as a second
sandbox provider; Temporal or BullMQ flows for long multi-step pipelines. Adopt only with a measured win on our
own tasks (same task, compare pass rate, cost, minutes).
