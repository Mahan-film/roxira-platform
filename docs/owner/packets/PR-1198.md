# بستهٔ تصمیم PR #1198

- **عنوان:** ماندگاری Redis (AOF) و جداسازی پایگاه دادهٔ صف و کش (`T217` / `#931`)
- **وضعیت و سرشاخه:** باز | `b7ddb316` | `MERGEABLE` (طبق `docs/STATE.md` دارای blocker از desk و نیازمند جملهٔ مالک).

## چه چیزی را تغییر می‌دهد
- در `docker-compose.prod.yml` سرویس `redis_prod` را به ذخیره‌سازی AOF (`--appendonly yes`، `everysec`) و سقف حافظهٔ `200mb` با سیاست `noeviction` مجهز می‌کند.
- DB 0 را برای صف‌های BullMQ و DB 1 را برای کش‌های موقت (OTP، rate limit، کش LLM) در `redis.provider.ts` و ماژول‌های پایتون جدا می‌کند.
- راهنمای `docs/ops/REDIS_DURABILITY.md` و تست `tests/test_redis_durability_compose.py` را اضافه می‌کند.

## چه چیزی ممکن است در production خراب شود
- با سیاست `noeviction` روی ۲۰۰ مگابایت، اگر کش یا صف‌ها پر شوند، نوشتن جدید در Redis با خطای OOM رد می‌شود (به‌جای پاک کردن کلیدهای قدیمی) و می‌تواند لاگین/OTP یا صف‌ها را متوقف کند.
- تغییر `docker-compose.prod.yml` و `app.module.ts` / `redis.provider.ts` اگر هم‌زمان روی همهٔ کانتینرها اعمال نشود، ممکن است سرویس‌ها به DB اشتباه وصل شوند.
- این PR هنوز یک blocker باز در review desk دارد که باید پیش از ادغام برطرف شود.

## نیاز به restart یا کار دستی
- بله: نیاز به recreate کردن کانتینر `redis_prod` و سرویس‌های مصرف‌کننده (NestJS و هستهٔ پایتون) با حجم (volume) پایدار AOF دارد.

## گام‌های بازگشت (Rollback)
- برگرداندن تغییر `docker-compose.prod.yml` و `redis.provider.ts` و اجرای دوبارهٔ `docker compose up -d`؛ در صورت پر شدن حافظه پیش از بازگشت، می‌توان موقتاً سیاست حافظه را با `CONFIG SET maxmemory-policy volatile-lru` تغییر داد.
