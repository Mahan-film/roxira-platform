## Behaviour: `POST enterprise-hub/sales/orders/:id/deliveries`
Body `{ deliveryDate: 'YYYY-MM-DD', idempotencyKey?: string(max 64), note?: string, lines: [{ orderLineId: number, quantity: number|string }] }`; quantity via `parseQuantityHundredths` (max 2 decimals, > 0; no rounding), at most 200 lines, no duplicate orderLineId.
All inside ONE `TenantScope` transaction (`SalesRepository.runInTransaction`/manager), nothing is committed unless everything succeeds:
1. If `idempotencyKey` is given and a delivery with that key exists for the tenant: return it unchanged (200 with the existing delivery, no stock movement, no voucher). Same body is not compared; the key is the identity.
2. Lock the order row `FOR UPDATE`. The order must be CONFIRMED (else 409). Order not found -> 404.
3. For each line: it must belong to the order (else 400); quantity must be <= open quantity = quantity - delivered_quantity (else 409, message in Persian, nothing partially applied). Over-delivery is refused.
4. For each line `issueStock` through InventoryService with the order's warehouse and `reference` = delivery number, passing the same manager; this consumes FIFO layers and lowers on-hand. Line cost = `toMinor(result.totalCost)` (bigint minor units, money.ts). Insufficient stock surfaces as the existing inventory error (map to 409) and rolls everything back.
5. Insert delivery + lines (line_cost per line, total_cost = sum bigint). Insert ONE stock document via `StockDocumentsRepository.insertDocument(tenantId, {...docType SALES_DELIVERY, status POSTED, docNumber `SD-${deliveryNumber}`.slice(0,40), docDate, fromWarehouseId, reference: deliveryNumber, postedAt}, lines, manager)` (see `recordStockDocument` in `modules/invoicing/services/invoice-posting.service.ts` for the field shapes), store its id in stock_document_id.
6. If total_cost > 0: post COGS via `PostingRulesService.post(tenantId, { docType: 'invoice.sale_cogs', sourceType: 'sales_delivery', sourceId: String(delivery.id), date, amounts: { cost: totalCost }, description, entryNumber: `DNC-${number}`.slice(0,64), overrides }, manager)`; store `entryId` in journal_entry_id. If total_cost is 0 post nothing.
7. `UPDATE erp_sales_order_lines SET delivered_quantity = delivered_quantity + $q` per line (the CHECK constraint is the last guard).
Response: delivery with lines (quantity, lineCost and unitCost = lineCost/quantity are exposed through money.ts `fromMinor`, never floats for the cost), `totalCost`, `journalEntryId`, `stockDocumentId`, `number`.
Other routes: `GET enterprise-hub/sales/deliveries?orderId=&partyCode=&limit=&offset=` (list with total), `GET enterprise-hub/sales/deliveries/:id`, and `GET enterprise-hub/sales/orders/:id/fulfilment` returning per order line `{ orderLineId, itemId, ordered, delivered, backorder }` with backorder = ordered - delivered (hundredths bigint maths) plus `status: 'NONE'|'PARTIAL'|'COMPLETE'` (NONE when delivered is 0 everywhere, COMPLETE when every backorder is 0). Also `GET enterprise-hub/sales/backorders?partyCode=` listing open lines of CONFIRMED orders with backorder > 0 `{ orderId, orderNumber, partyCode, itemId, backorder }`. Decorators like the other sales GETs (INVOICING, AlsoAllow ACCOUNTING); the POST is INVOICING write. Regenerate the matrix: `UPDATE_PERMISSION_MATRIX=1 npx jest modules/access/permission-matrix.spec.ts --maxWorkers=2`, keep only added rows.
Delivering does not change reservation semantics: reserved is open quantity, so a delivery lowers reserved and on-hand by the same amount and available stays the same (assert it).
